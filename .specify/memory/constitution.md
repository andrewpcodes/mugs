# Mugs Constitution

## Core Principles

### I. Contract-First API

- `api-specification.yml` (OpenAPI 3) is the single source of truth for every HTTP endpoint,
  request/response schema, status code, and security requirement.
- Any API change MUST be made in `api-specification.yml` first; implementation follows the spec,
  never the reverse.
- Request/response models MUST be generated by the OpenAPI Generator Gradle task into
  `com.overmild.mugs.models`; hand-written DTOs that duplicate spec schemas are prohibited.
- Error responses MUST use `application/problem+json` (`ProblemDetail`) as declared in the spec.
- Breaking changes to existing operations (removed fields, changed types, new required inputs)
  MUST be called out explicitly in the feature spec and coordinated with the frontend.

Rationale: a separate frontend consumes this API; a single, generated contract prevents drift.

### II. Test-Backed Behavior

- Every endpoint behavior MUST be covered by Spock specifications under `src/test/groovy`,
  including success paths, validation failures (400), auth failures (401/403), and not-found (404).
- New or changed behavior MUST land with its tests in the same change; `./gradlew test` MUST pass
  before merge.
- Tests MUST NOT depend on external services (e.g., the live Supabase issuer); JWTs are mocked
  with Spring Security test support.

Rationale: a small API with no QA team relies on tests as its only regression safety net.

### III. Secure by Default

- Mutating endpoints (POST, PUT, PATCH, DELETE) MUST require an authenticated JWT validated for
  both issuer and audience.
- Unauthenticated access is permitted only where explicitly declared in the OpenAPI spec and
  mirrored in `SecurityConfig`; new routes default to authenticated.
- Operations on owned resources MUST verify that the JWT subject is authorized for that resource
  (e.g., mug owner) in the service layer, not only in the client.
- Secrets, tokens, and environment-specific URLs MUST be supplied via environment variables;
  none may be committed. CORS origins MUST be explicitly configured, never wildcarded with
  credentials.

Rationale: the API is internet-reachable from a home device; least privilege limits blast radius.

### IV. Layered Simplicity

- Code MUST follow the existing layering: `controllers` → `services` → `repositories`, with
  `mappers` (MapStruct) translating between entities and generated models.
- Controllers MUST contain no business logic or SQL; repositories MUST contain no HTTP concerns.
- Persistence uses Spring JDBC with explicit SQL; introducing an ORM, new framework, or new
  infrastructure dependency MUST be justified in the feature plan.
- YAGNI: build only what a current spec requires; no speculative abstractions or options.

Rationale: a small codebase stays maintainable when every class has one obvious home.

### V. Portable, Lightweight Deployment

- The application MUST run as a single Docker container on Raspberry Pi (ARM64) as well as
  x86_64, with SQLite persisted on a mounted volume.
- Schema changes MUST be expressed in `schema.sql` and be idempotent and backward-compatible with
  existing data (e.g., `CREATE ... IF NOT EXISTS`, additive columns with defaults); destructive
  migrations require an explicit migration note in the feature plan.
- All runtime configuration MUST be overridable via environment variables with sane defaults in
  `application.properties`.
- Resource usage MUST stay appropriate for a low-memory single-board computer; avoid features
  that require additional always-on services.

Rationale: the deployment target is a constrained home server, not a cloud cluster.

## Technology Constraints

- Language/runtime: Java 21 (Gradle toolchain), Spring Boot 4.x (Web MVC, Security OAuth2
  Resource Server, JDBC, Validation).
- Persistence: SQLite via `sqlite-jdbc` with foreign keys enforced (`PRAGMA foreign_keys=ON`).
- Code generation: OpenAPI Generator (spring generator, models only, Jakarta EE, bean validation).
- Mapping and boilerplate: MapStruct and Lombok.
- Testing: Spock 2.x on the JUnit Platform with Spring Boot test slices.
- Identity provider: Supabase-issued JWTs; issuer and audience are configuration, not code.
- Packaging: Dockerfile + Docker Compose; images published to GitHub Container Registry.

Adding or replacing any item above is a governance-relevant change and MUST be justified in the
relevant feature plan's complexity tracking.

## Development Workflow

- Features follow the Spec Kit flow: `/speckit-specify` → `/speckit-clarify` (as needed) →
  `/speckit-plan` → `/speckit-tasks` → `/speckit-implement`.
- Each plan MUST include a Constitution Check against Principles I–V; any violation MUST be
  recorded with justification in the plan's complexity tracking table.
- Implementation order for API features: update `api-specification.yml` → regenerate models →
  write/extend Spock specs → implement repository/service/controller → update `schema.sql` if
  needed.
- Before merge: `./gradlew build` passes (compile, generation, tests) and the Docker image builds.
- Commits are small and focused, with imperative-mood messages.

## Governance

- This constitution supersedes conflicting conventions, docs, and ad-hoc practices in this
  repository.
- Amendments are made via `/speckit-constitution`, recorded in this file with a Sync Impact
  Report during review, and committed alongside any affected guidance.
- Versioning follows semantic versioning:
  - MAJOR: removal or backward-incompatible redefinition of a principle or governance rule.
  - MINOR: a new principle or section, or materially expanded guidance.
  - PATCH: clarifications, wording, and typo fixes with no change in meaning.
- Compliance: every feature plan and code review MUST verify adherence to the Core Principles;
  deviations require written justification or an amendment.
- Runtime development guidance lives in `README.md` and agent guidance files (e.g., `CLAUDE.md`)
  and MUST NOT contradict this constitution.
